# SRP — 요구사항 명세 프롬프트

## 최종 작성 프롬프트

```text
첨부한 CRS v0.1을 바탕으로 학생용 개인 과제 관리 프로그램의 SRS를 작성해줘. 이번 결과물은 CRS가 아니라 SRS이고, 유스케이스 기술서도 SRS 안에 포함해줘. 최종 문서는 docs/SRS_요구사항명세_초안.md에 저장할 수 있도록 한국어 마크다운으로 작성해줘.

CRS는 요구사항의 근거로 읽어줘. 표의 작성 가이드나 서식 안내는 고객 요구사항으로 취급하지 말고, 팀 제안과 강사의 실제 답변도 구분해줘. 실제 답변이 비어 있는 Q는 미확정으로 남겨줘. 자료에 없는 정책이나 예외 동작을 임의로 확정하지 말고, CRS가 C1·C4·C5를 번호로만 언급하고 별도 정의를 제공하지 않은 경우에도 범위 표에 적힌 내용만 반영해줘.

핵심 범위는 과목·과제 제목·마감일 등록, 미완료 과제를 마감이 가까운 순서로 조회, 과제 완료 처리, 완료 과제 별도 조회, 기한이 지난 미완료 과제 보존, 잘못된 입력 안내와 기존 데이터 보호야. 로그인·자동 알림·학습 시스템 연동·영구 저장·과제 수정 및 삭제·완료 취소는 제외해줘. 과제 데이터가 프로그램 실행 중에만 유지된다는 점도 명시해줘.

문서는 시스템 목적과 범위, 액터, 기능 요구사항, 사용자 목표와 유스케이스 목록, 유스케이스 다이어그램, 유스케이스 기술서, 데이터·상태 규칙, 비기능 요구사항과 제약, CRS 요구사항 추적표, 고객 확인 사항 순으로 정리해줘. 액터는 학생으로 두고, 고객이라는 이유만으로 강사를 액터에 넣지 마.

유스케이스는 과제 등록, 미완료 과제 목록 확인, 과제 완료 처리, 완료 과제 목록 확인으로 구성해줘. 각 항목의 ID와 이름은 목록·다이어그램·기술서에서 일치시키고, 고객 요구 CR과 기능 요구사항 ID도 연결해줘. 다이어그램은 PlantUML 코드로 작성하고 미리보기를 실제 확인하지 않았다면 확인한 것처럼 쓰지 마.

각 유스케이스 기술서에는 목표, 액터, 근거, 사전조건, 시작 사건, 성공·실패 후 결과, 기본 흐름, 대안·예외 흐름, 미확정 사항을 포함해줘. 기본 흐름에는 액터의 행동과 시스템 응답을 단계별로 적고, 대안·예외 흐름에는 분기 조건과 기본 흐름의 관련 단계, 응답, 복귀 또는 종료 결과를 써줘. 버튼이나 입력 검사를 별도 유스케이스로 나누지는 마.

과제 완료 처리 UC는 특히 자세히 써줘. 정상 처리 전후에 과제가 미완료·완료 목록에서 어떻게 보이는지 분명히 하고, 존재하지 않는 과제를 선택한 경우, 이미 완료된 과제를 다시 선택한 경우, 마감일이 지났지만 미완료인 과제를 처리하는 경우를 각각 검토해줘. CRS에 근거가 있는 동작은 반영하고, 근거가 없는 응답이나 복구 방법은 정하지 마. 기존 Q와 맞지 않는 확인 사항이 새로 드러나면 기존 Q ID를 다른 뜻으로 재사용하지 말고, SRS에는 추가 확인 제안으로 표시해 CRS 질문표 보완이 필요하다고 적어줘.

CRS의 Q-01(마감일이 같은 과제의 정렬), Q-02(잘못된 날짜 입력 뒤 이동·재입력 방식), Q-03(잘못 완료 처리한 과제의 구제책)은 해당 유스케이스에 [논의] Q-XX로 연결해줘. 팀 제안은 제안으로 표시하고, 강사의 답변처럼 쓰지 마. 기존 과제 데이터 보존 요구를 지키고, 기한이 지났다는 이유만으로 미완료 과제를 삭제하거나 완료 처리하지 마.

표와 섹션을 읽기 쉽게 구성하고, CR·NEEDS·C·Q·UC·FR ID를 서로 혼동하지 않게 해줘. 팀명·팀원·작성일·버전은 제공된 자료에서 확인되는 값만 쓰고 모르는 값은 미기재로 둬. 템플릿의 작성 안내와 빈칸 표시는 최종 문서에서 제거해줘. 문장은 짧고 자연스러운 한국어로 쓰고, 요청에 없는 기능이나 과장된 설명은 덧붙이지 마.
```
